# RFC process

An RFC is required for changes that add a major capability, alter a public
contract, impose a runtime dependency, or significantly affect project
structure.

An RFC should state:

1. The problem and concrete use cases.
2. The proposed public API and lifecycle impact.
3. Alternatives considered.
4. Backward-compatibility and performance implications.
5. A testing and rollout plan.

Small fixes, internal refactors, documentation, and implementations of already
accepted roadmap items do not require a separate RFC unless they change a
public contract.
